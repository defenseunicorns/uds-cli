## What you'll accomplish

Use an AI coding agent to make a reviewable first-pass migration from a Legacy
`uds-bundle.yaml` to UDS CLI Next HCL files. You
will review the generated migration report, validate the files with UDS CLI, and
optionally deploy to a non-production cluster.

## Prerequisites

- [UDS CLI installed](/cli/getting-started/installation/).
- An AI coding agent that can read the migration skill from this repository or
  its upstream URL. You can also supply the skill file directly.
- A Legacy bundle source directory containing `uds-bundle.yaml`.
- Access to the source packages and their trust material for bundle creation.
- A non-production cluster only when you are ready to test a deployment. Standard
  Zarf packages require an initialized cluster, or a migrated bundle that includes
  the Zarf `init` package before packages that require it. Check each package's
  deployment mode; connected and cluster-less packages have different requirements.

> [!WARNING]
> This AI-assisted migration workflow is experimental. The agent generates a
> first-pass proposal, not an attestation that the result is safe or equivalent.
> Review generated files, package sources, variable behavior, Zarf mappings, package
> signature verification, and every item in the migration report before using the
> result in any environment. A successful artifact build does not prove deployment
> equivalence.

## Steps

<Steps>

1. **Start the agent and confirm the skill**

   Start your coding agent from your working directory. If you have a repository
   checkout, start from its root.

   Ask the agent to read
   `.agents/skills/migrate-legacy-bundle-to-next/SKILL.md` or the upstream URL
   included in the printed prompt, state its name, and
   summarize its required output without changing files. It should identify the
   `migrate-legacy-bundle-to-next` skill and say it produces proposed HCL files
   and a migration report.

   If your agent does not discover repository-local skills, provide that `SKILL.md`
   file directly in the agent's supported way. The skill is plain Markdown, so you
   can also paste its contents into the conversation.

2. **Generate the Next files**

   Print the migration prompt:

   ```bash
   CLI_FEATURES=NextMode=true uds bundle migrate prompt
   ```

   For a short explanation of verification, signing, and testing without opening
   this guide, run:

   ```bash
   CLI_FEATURES=NextMode=true uds bundle migrate prompt --help
   ```

   Paste it into your agent, replacing `./legacy/uds-bundle.yaml` with your Legacy
   bundle path. The prompt writes the proposed files to `./.next`. Use a new output
   directory for each migration; move an existing `.next` directory before starting.

   Expect `bundle.uds.hcl` and `migration-report.md`. The agent also generates
   values files and `defaults.uds.hcl` when needed. Deployment settings from
   `uds-config.yaml` remain a separate task.

   Compare the generated packages with the Legacy bundle and read the report.
   Ask the agent to explain anything marked for review. If your bundle uses
   overrides, the agent may need the packages' `zarf.yaml` files to check their
   values mappings. Keep private keys and credentials out of the prompt.

3. **Review package verification and choose bundle signing**

   Package verification and bundle signing serve different purposes:

   - **Package verification:** Each package's `signature_verification` block
     controls whether you trust the package being included. Keep any migrated
     public-key or keyless settings. The agent carries over the Legacy policy
     without adding alternative options. If the Legacy package has no policy,
     the agent omits the block and reports it as a blocker for bundle creation.
   - **Bundle signing:** The create command signs the finished bundle with
     `--signing-key` or `--keyless`. For a local alpha test, `--unsigned` creates
     an artifact without a bundle signature.

   Next requires a verification policy for every package at create time. Resolve
   missing policies with the package owner before testing; the migration does not
   choose one for you. `--unsigned` does not change package verification.

   See [Sign and verify a bundle in Next mode](/cli/how-to-guides/next/sign-bundle-artifacts/)
   when you are ready to create a signed artifact.

4. **Try creating the bundle**

   From your working directory, run this local alpha check against the generated
   directory:

   ```bash
   CLI_FEATURES=NextMode=true uds bundle create ./.next --unsigned
   ```

   This reads the HCL, validates package policies, and retrieves package content.
   It may access registries, but it does not deploy to a cluster. If you need a
   specific target architecture, add `--architecture amd64` or `--architecture arm64`.

   A failure can still give useful feedback. If the command reaches `ingesting
   package`, the definition passed parsing and create-time validation. A later
   registry connection or package-loading error does not mean the HCL is invalid,
   but you still need to resolve it before creating an artifact. A local authoring
   directory may need to be built into a Zarf package archive first.

   Share the output with the agent and ask it to explain the failure and the next
   step. Record any testing changes in the migration report. A successful create
   writes a `.tar.zst` artifact beside `bundle.uds.hcl`; this local test artifact
   is unsigned.

</Steps>

## Verification

Confirm that the generated definition accounts for the Legacy packages and that
you understand each unresolved item in the report. Reaching package ingestion
confirms the HCL and package policies passed validation; completing creation
also confirms the package sources could be assembled into an artifact.

The migration skill stops at artifact creation and does not perform cluster
operations. When you are ready to test workload behavior as a separate task, follow
[Deploy a bundle in Next mode](/cli/how-to-guides/next/deploy-a-bundle/) using a
non-production cluster. Review package dependencies and cluster initialization
first: package list order does not establish deployment order. If an agent will
run the deployment, explicitly authorize that cluster operation.
